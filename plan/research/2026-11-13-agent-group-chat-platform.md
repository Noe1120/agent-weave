> 当前完整设计：`../README.md`（2026-11-14 v1.6）。本文保留为前期调研，后续实施以完整设计包为准。

日期：2026-11-13（Asia/Tokyo）。状态：讨论草案，尚未开始实现。

本稿根据用户补充更新产品定位。此前多 Agent 工作台调研保留为代码执行层参考；本稿优先描述建群、邀请 agent、用户分工、共享项目记忆和成员互助。下面的实现方式均为设计建议。参考项目仅核验公开文档，尚未安装或验证客户端兼容性。

## 1. 已确认的产品目标

用户希望构建类似微信的平台：由用户创建群聊，邀请不同 agent 作为群成员，围绕同一个项目合作。用户决定各成员的职责，并可以随时调整。DeepSeek Harness 规划、Claude Desktop 前端、Codex 后端只是示例，不能固化为默认能力排名或唯一分工。

同群 agent 共享项目数据库和上下文，能够询问彼此、请求协助、评审成果，并共同完成交付。

建议的产品定义：一个由用户组织、不同 agent 共同参与、以项目群为中心的协作应用。聊天是主要入口，任务、文件、共享记忆和验收是群内的工作能力。

## 3. 用户应该看到的产品

建议主界面为三栏：

- 左侧：群聊列表、未读与待处理事项，以及可邀请的 agent。
- 中间：项目群消息；支持 @、引用、话题回复、附件和任务卡片。
- 右侧：群成员职责与状态、项目计划、共享记忆、文件与验收入口。

建议最小产品对象：

- 用户：建群、邀请、分工、暂停、修改目标、决定超出既有范围的变更。
- Agent 档案：厂商/harness、连接方式、已验证的工具能力、可选模型与设置。
- 群成员：一个具体 agent 会话在本群的身份、职责、权限和运行状态。同一产品可以有多个独立成员实例。
- 项目群：成员集合、项目关联、群规则、共享消息和记忆。
- 任务：明确的目标、负责人、协作者、依赖和验收条件。
- 产物：代码提交、设计文档、截图、测试证据等。

角色由用户定义。即使用户把一个成员设为规划者，也不意味着它自动拥有修改其他成员职责、扩展项目范围或无限派工的权限。

## 4. 一个预期使用场景

以下是设计示例，角色沿用用户举例，不代表功能已实现。

1. 用户新建“商店网站”群，关联项目目录。
2. 邀请 DeepSeek Harness、Claude Desktop、Codex，分别设定规划、前端、后端职责。
3. 用户发出目标；规划成员提出计划和接口约定；成员在群内补充，用户确认关键取舍。
4. 分工记录为任务，相关成员开始工作；所有人可见任务负责人和状态。
5. 前端成员在具体任务话题中 @ 后端成员，询问接口字段；回复关联接口版本并写入共享决策。
6. 后端成员遇到设计问题，请规划成员帮忙；协助结果回到原任务，不转移原任务的责任归属。
7. 成员提交代码和测试证据；群里出现可打开的产物卡片。
8. 组合改动通过验收后，群内发布最终结果和剩余事项。

不需要用户复制信息给多个 agent，也不把每一条普通聊天直接解释为修改代码的指令。

## 5. “共享数据库与上下文”的具体设计

### 5.1 一个权威的群数据服务

建议同群共享一份持久化项目记录，由服务统一处理读写。agent 通过 API/MCP 读写，避免直接操作任意业务表。

逻辑数据包括：群与成员、消息与回复、任务与依赖、决策与规范、产物与测试证据、成员读取游标、运行状态和事件。

本地原型可从单服务加 SQLite 开始；以后如需多人远程使用，再评估服务器部署与 PostgreSQL。通过接口隔离存储实现，不在第一版引入全部分布式设施。

所有读写都按 room_id / project_id 校验归属。同一 agent 参与多个群时，不自动把另一个群的上下文带进来。

这里的协作数据库与用户项目本身的业务数据库是两个概念。若用户希望共同操作项目业务数据库，应另外明确开发环境、权限和迁移责任。

### 5.2 公共记忆与本次输入分开

建议共享三层信息：

| 层次 | 内容 | 更新规则 |
| --- | --- | --- |
| 群历史 | 原始消息、附件、任务事件 | 保留来源、作者、时间和引用关系 |
| 项目记忆 | 已确认目标、规范、接口、决策、待解决问题 | 有版本、有依据；草案与确认记录分开 |
| 成员当前任务上下文 | 本次需要的消息增量、项目记忆版本、依赖结果与代码版本 | 开始执行及恢复时生成，成员可以继续查询原文 |

设计上让所有成员访问同一套事实，但不要求每次调用都携带整段群历史。每个成员记录已读取位置和采用的记忆版本；关键决策变更主动通知受影响任务。尚未读取最新变更的成员可以显示为“待同步”。

新成员入群时发放 onboarding 包：目标、已确认分工、当前任务、关键决策、相关文件和未解决事项，并保留原消息索引供核查。

## 6. 群消息如何变成协作动作

建议使用以下默认策略，允许用户在群设置中调整：

- 普通消息：持久化并可查阅，不强制所有成员回复。
- @ 成员：向指定成员投递一次处理请求；忙碌时进入其收件队列。
- @ 全体讨论：开启一次有边界的讨论，成员按顺序给出意见，再汇总。
- 分配任务：在用户既定职责与范围内记录负责人、依赖和验收条件，然后执行。
- 请求协助：创建关联原任务的协助事项，明确希望对方回答、评审还是修改文件。
- 提交成果：登记实际产物和检查证据，进入验收。
- 改变目标/职责：按用户的群权限规则处理，不由普通聊天隐式覆盖。

平台调度服务负责可靠投递、排队、去重和状态变化；用户可以指定一个 agent 做规划或协调，但不把群的数据一致性寄托在它是否记得全部聊天上。

每个消息事件有唯一 ID；运行记录关联触发消息。收件、已读、开始处理和完成是不同状态。agent 断线后可以恢复未读；消息重复投递不得重复执行同一个任务。

自动互助设定可调的回合数、并发数、时间/用量上限和终止条件。用户在群内可以暂停单个成员或整组工作。

## 7. 成员互助与代码交付

建议支持四种互助：澄清接口、提供方案、评审产物、承担有边界的协助任务。每项任务仍保留一个明确负责人。

若协助只需要给意见，就在原任务话题中回复。若需要改代码，就建立关联子任务，明确文件范围与交接方式，再提交可审查的改动。

项目群共享一个逻辑项目；代码层建议保留每任务独立 worktree 的办法。这样成员共享规范与结果，同时能分别追踪代码改动。数据库里的“任务完成”必须由产物和验收状态支撑。

## 8. 接入必须验证的四个层次

| 层次 | 验证问题 |
| --- | --- |
| 入群 | 原客户端能否连接群服务并使用正确的成员身份？ |
| 收发 | 能否读群消息、发消息、获取共享上下文和附件？ |
| 唤醒 | 忙碌、空闲、回合结束或重启后，新消息能否触发实际处理？ |
| 执行 | 能否在指定项目内读写文件、运行命令、返回可核验产物？ |

Claude Desktop 官方文档确认本地 MCP/扩展接入。[R6] 这为读写群数据提供路径，但仅凭 MCP 连接成功，不能确认它在所有状态下都能自动收消息并继续执行；本地 Agent Chat 的 README 也明确提示客户端唤醒限制。[R3]

因此，第一版应真实显示“可自动响应”“需要手动唤醒”“离线”等能力与状态。保留用户所说的 Claude Desktop 作为独立验证对象，不未经确认就用 Claude Code 或 Claude API 替代。

如果选择由平台托管 harness 进程，则可另设运行适配器；群成员仍沿用同一个身份、消息和任务模型。是否必须使用原客户端，是实现前最关键的待确认项。

## 9. 最小验证版本

第一阶段只验证：建一个群、邀请三个目标 agent、用户指定职责、在同一群里往返消息、共享一条决策、完成一次 agent 间求助，并在重启后恢复历史。

第二阶段绑定一个小项目：把群内分工变成任务，收集真实代码产物与测试结果，完成一个包含前后端的功能。

第三阶段再扩展多人账户、跨机器运行、自动团队模板、更多 agent 和更细的用量管理。

关键验收用例：

1. 用户在群里变更一个已确认接口；受影响成员获取到同一个新版本。
2. 一个成员 @ 另一个成员请求帮助；得到关联原消息的结果，其他无关成员不会循环回复。
3. 一个成员退出后重新入群；能恢复职责、任务和未读进度。
4. 两个成员同时领取同一任务；只产生一个有效负责人。
5. 所有成员都声称完成，但组合测试失败；群里的项目状态仍显示待修复。
6. 同一 agent 加入另一项目群；不能误读取前一个群的数据。

## 10. 仍待确认

第一版是否必须直接连接用户已经安装并登录的原版客户端，尤其是 Claude Desktop？这决定原客户端的监听/唤醒验证是否是硬性验收项，以及托管 harness 是否可作为可接受的接入方式。

此项不影响群聊、共享数据和用户分工的产品定义，但会显著影响连接器设计。
